## 新增需求

### 需求: Wiki 反馈收件箱
系统必须在 Wiki 运营能力中提供用户反馈收件箱。

#### 场景: 查看新反馈
- **当** 管理员进入 Wiki 反馈收件箱
- **那么** 系统必须展示未处理反馈列表
- **并且** 每条反馈必须展示反馈类型、负反馈原因、用户补充内容、关联问题、机器人回答和创建时间

#### 场景: 查看反馈证据
- **当** 管理员打开反馈详情
- **那么** 系统必须展示关联回复的 Wiki 检索 query、命中文档、命中数量、耗时和错误信息
- **并且** 如果没有关联回复，系统必须明确标识该反馈无法反查原始回答

### 需求: 反馈分流
系统必须允许管理员对反馈进行分流处理。

#### 场景: 标记为知识缺失
- **当** 管理员将反馈标记为知识缺失或内容不完整
- **那么** 系统必须允许管理员从该反馈创建 Wiki 草稿

#### 场景: 标记为检索问题
- **当** 管理员将反馈标记为检索问题
- **那么** 系统必须保存处理状态和备注
- **并且** 禁止自动创建 Wiki 草稿

#### 场景: 标记为模型或工具问题
- **当** 管理员将反馈标记为模型问题、工具问题或数据分析错误
- **那么** 系统必须保存处理状态和备注
- **并且** 该反馈必须继续计入质量指标

#### 场景: 忽略反馈
- **当** 管理员确认某条反馈无需处理
- **那么** 系统必须将反馈标记为已忽略
- **并且** 保存忽略原因

### 需求: 反馈转 Wiki 草稿
系统必须支持从用户反馈创建待审核 Wiki 草稿。

#### 场景: 从负反馈创建草稿
- **当** 管理员选择将负反馈转为 Wiki 草稿
- **那么** 系统必须预填目标 namespace、建议页面路径、原问题、原回答、反馈内容、负反馈原因和检索证据
- **并且** 草稿来源类型必须为 `feedback-event`

#### 场景: 草稿创建后关联反馈
- **当** 反馈成功创建 Wiki 草稿
- **那么** 系统必须将反馈状态更新为已生成草稿
- **并且** 保存草稿 ID 以便从反馈详情跳转到草稿审核

### 需求: 反馈运营指标
系统必须提供反馈质量指标，帮助管理员判断知识库和机器人质量趋势。

#### 场景: 查看反馈统计
- **当** 管理员查看 Wiki 运营页
- **那么** 系统必须展示选定时间窗口内的正反馈数、负反馈数、负反馈率、待处理反馈数和已转草稿数

#### 场景: 按原因聚合负反馈
- **当** 管理员查看负反馈原因分布
- **那么** 系统必须按企业微信负反馈原因聚合数量
- **并且** 区分知识缺失、检索问题、模型/工具问题和已忽略反馈
