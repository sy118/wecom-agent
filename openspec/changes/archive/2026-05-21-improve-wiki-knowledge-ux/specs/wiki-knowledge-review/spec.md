## 新增需求

### 需求: 反馈证据驱动处理
系统必须在反馈详情中按照证据链组织信息，帮助管理员判断反馈根因。

#### 场景: 查看反馈证据链
- **当** 管理员打开用户反馈详情
- **那么** 页面必须展示用户反馈类型、负反馈原因、用户补充内容、原问题、机器人回答、关联会话和检索证据
- **并且** 页面必须突出可执行处理动作，例如标记检索问题、标记模型或工具问题、转 Wiki 草稿、创建标注答案或忽略

#### 场景: 反馈无法关联回答
- **当** 反馈没有关联回复追踪记录
- **那么** 页面必须明确展示未关联状态
- **并且** 禁止把该反馈伪装成可自动反查证据的反馈

### 需求: 三栏草稿审核
系统必须在草稿详情中提供来源证据、草稿内容和合并差异的并列审核体验。

#### 场景: 审核来源型草稿
- **当** 管理员打开待审核草稿详情
- **那么** 页面必须展示草稿来源证据、可编辑草稿内容和合并前差异预览
- **并且** 管理员必须能够在同一审核界面保存草稿、切换合并策略、批准合并或拒绝草稿

#### 场景: 小屏审核布局
- **当** 页面宽度不足以展示三栏审核
- **那么** 系统必须将来源证据、草稿内容和合并差异改为纵向区域或分段展示
- **并且** 禁止让按钮、文本或预览内容发生不可读重叠

### 需求: 反馈到草稿的状态联动
系统必须让反馈处理项、草稿和合并结果之间保持可追踪的状态联动。

#### 场景: 从反馈创建草稿后
- **当** 管理员从反馈详情创建 Wiki 草稿
- **那么** 页面必须跳转或打开对应草稿审核界面
- **并且** 反馈项必须展示已转草稿状态和草稿引用

#### 场景: 反馈来源草稿合并后
- **当** 管理员批准合并来源为反馈的草稿
- **那么** 页面必须将关联反馈展示为已解决
- **并且** 待办和总览中的反馈待处理数量必须刷新
