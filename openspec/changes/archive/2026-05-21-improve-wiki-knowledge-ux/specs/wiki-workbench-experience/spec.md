## 新增需求

### 需求: Wiki 工作台信息架构
系统必须将 Wiki 管理页面组织为面向知识运营的工作台，并保持现有管理台视觉风格。

#### 场景: 进入 Wiki 工作台
- **当** 管理员访问 `/wiki`
- **那么** 页面必须展示全局行动总览、配置清单、知识库空间列表和当前 namespace 工作区
- **并且** 工作区必须提供文档、待办、反馈闭环、配置和分析等入口

#### 场景: 保持当前页面风格
- **当** 系统展示 Wiki 工作台的新区域
- **那么** 页面必须优先使用现有 Ant Design 组件和当前后台风格
- **并且** 禁止引入营销式 hero、全新视觉体系或与当前控制台明显割裂的布局

### 需求: 行动总览
系统必须在 Wiki 页面首屏提供可操作的总览，帮助管理员判断今天最值得处理的问题。

#### 场景: 展示待处理摘要
- **当** Wiki 页面加载完成
- **那么** 行动总览必须展示待处理反馈、待审核草稿、高频无命中问题和配置异常的数量
- **并且** 每个摘要项必须提供跳转或筛选到对应处理区域的操作

#### 场景: 没有待处理事项
- **当** 当前 Wiki 没有新反馈、待审核草稿、高频无命中或配置异常
- **那么** 行动总览必须展示稳定运行状态
- **并且** 提供测试检索、上传文档或查看分析的轻量入口

### 需求: 统一待办收件箱
系统必须将草稿、用户反馈、无命中问题和配置异常聚合为统一待办列表。

#### 场景: 查看统一待办
- **当** 管理员打开 Wiki 待办区域
- **那么** 系统必须展示来自草稿、反馈、无命中和配置体检的待办项
- **并且** 每个待办项必须展示来源类型、影响对象、推荐动作、当前状态和创建或更新时间

#### 场景: 处理待办后刷新状态
- **当** 管理员完成合并草稿、忽略反馈、创建草稿或修复配置等操作
- **那么** 系统必须刷新对应待办状态
- **并且** 更新总览中的待处理数量

### 需求: Namespace 上下文保持
系统必须在切换工作区时保持当前 namespace 上下文，避免管理员重复选择。

#### 场景: 切换工作区
- **当** 管理员在同一个 namespace 下从文档切换到待办、反馈闭环、配置或分析
- **那么** 页面必须保持当前 namespace 选择
- **并且** 工作区数据必须围绕当前 namespace 展示
