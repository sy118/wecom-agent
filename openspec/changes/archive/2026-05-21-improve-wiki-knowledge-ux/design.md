## 上下文

当前 Wiki 页面已经基于 Ant Design 实现了较完整的管理能力：顶部标题与操作、配置体检中心、知识库空间卡片、namespace 详情区、文档与搜索、绑定、健康状态、知识草稿、反馈、标注答案和运营 Tab。

主要问题不是能力缺失，而是信息架构偏“模块罗列”。用户进入页面后需要自己判断：

- 当前 Wiki 到 Bot 的链路是否可用；
- 哪些知识问题最值得今天处理；
- 负反馈、无命中、草稿审核之间是什么关系；
- 审核草稿时为什么要改、改哪里、改完会影响什么；
- 配置异常应该从哪里修复。

因此这次设计不追求重做视觉，而是在现有页面风格上重新组织工作流，让页面从“知识库配置页”变成“机器人知识质量运营台”。

目标用户是平台管理员、知识库维护者和负责机器人回答质量的运营人员。他们通常不是每天都修改系统配置，但会周期性处理反馈、补充知识、审核草稿和排查检索效果。

## 目标 / 非目标

**目标：**

- 沿用当前 Ant Design 管理台风格，包括 Card、List、Tabs、Modal、Statistic、Alert、Tag、Descriptions、Tree、Upload 等组件。
- 在 `/wiki` 首屏提供行动化总览，让管理员快速知道当前是否可用、今天要处理什么。
- 将反馈、无命中、草稿和配置异常聚合成统一待办，降低用户在多个 Tab 中来回寻找问题的成本。
- 优化文档工作区，让搜索、目录树、预览和编辑入口更连贯。
- 优化反馈详情和草稿审核，形成证据驱动的知识修复流程。
- 保持现有 API 和数据模型优先，只有在聚合待办性能不足时再增加轻量 API。

**非目标：**

- 不重做全站设计系统，不引入新的 UI 框架或复杂可视化库。
- 不改变 Wiki MCP Server、Git 合并、反馈入库和回复追踪的核心业务语义。
- 不在本变更中实现协同编辑、版本对比历史浏览、全文语义搜索或富文本编辑器。
- 不把 Wiki 页面做成营销式 landing page；它仍然是密集、可操作的后台工作台。

## 决策

### 决策 1：采用“总览 + 待办 + 工作区”的信息架构

新的 `/wiki` 页面保留左侧知识库空间列表和右侧 namespace 详情，但右侧 Tab 应围绕工作流重组：

```text
Wiki 知识库
├─ 顶部：行动总览 / 配置清单 / 新建知识库 / 同步最新
├─ 左侧：知识库空间列表
└─ 右侧：当前 namespace 工作区
   ├─ 文档
   ├─ 待办
   ├─ 反馈闭环
   ├─ 配置
   └─ 分析
```

替代方案是保留当前 `documents / health / drafts / feedback / annotations / ops` Tab，只在每个 Tab 里优化细节。这个方案改动小，但不能解决“用户不知道先处理什么”的核心问题。因此选择以待办和总览为中心重组。

### 决策 2：待办中心聚合已有数据，不先引入新表

统一待办可以由现有数据派生：

- 待审核草稿：`wiki_knowledge_drafts.status = pending`
- 新反馈/已分流反馈：`wiki_feedback_items`
- 高频无命中：`wiki_retrieval_logs` 聚合结果
- 配置异常：全局健康和 namespace 健康结果

前端可以先复用现有 API 并在页面内聚合；如果实现后发现请求过多或排序逻辑复杂，再新增 `/api/wiki/:namespace/action-items` 之类的聚合接口。

替代方案是创建独立 `wiki_action_items` 表。它能沉淀统一状态，但会引入同步一致性问题，并且当前待办都能从已有事实数据推导，暂不需要新表。

### 决策 3：草稿审核采用三栏心智，但视觉仍使用当前 Modal/Card 风格

草稿详情可以继续使用 Modal，但内部布局调整为：

```text
┌────────────────────────────────────────────────────────────┐
│ 草稿详情                                                   │
├──────────────┬──────────────────────┬──────────────────────┤
│ 来源证据      │ 草稿内容              │ 合并差异 / 合并后预览 │
│ 原问题        │ Markdown 编辑          │ append/replace/create │
│ 原回答        │ 目标路径/策略          │ 错误提示              │
│ 检索证据      │ 保存草稿              │ 合并/拒绝             │
└──────────────┴──────────────────────┴──────────────────────┘
```

替代方案是跳转到独立审核页面。独立页面空间更大，但当前 Wiki 主要操作都在一页内完成，Modal 更符合现有交互习惯。若三栏在小屏上拥挤，可在移动端降级为纵向折叠区块。

### 决策 4：反馈处理用“证据 + 判断 + 动作”

反馈详情不只展示字段，而是按处理流程组织：

1. 用户反馈：类型、原因、补充内容、时间；
2. 关联回答：原问题、机器人回答、Context；
3. 检索证据：query、命中文档、耗时、错误；
4. 判断：知识缺失、检索问题、模型/工具问题、忽略；
5. 动作：转草稿、创建标注答案、标记已处理。

替代方案是在列表行上放更多快捷按钮。快捷按钮适合熟练用户，但对反馈根因判断不够安全；保留列表快捷动作，同时把详情作为主处理入口。

### 决策 5：配置向导升级为持续清单

首次向导仍可存在，但配置状态应在页面顶部长期可见：

```text
WIKI_ROOT ✓  Git ✓  wiki-mcp !  MCP Server ✓  Namespace ✓  Context 绑定 !  检索测试 ?
```

每个异常项提供当前风格的按钮或链接，例如“注册 MCP Server”“新增绑定”“测试检索”“重启 Bot”。这样用户不是只在第一次进入时被引导，而是在后续配置漂移时也能快速修复。

## 风险 / 权衡

- [风险] 聚合待办可能让页面首屏请求变多 → 先复用现有并行请求，必要时增加轻量聚合 API。
- [风险] 重组 Tab 会影响已有用户肌肉记忆 → 保留原能力入口和文案映射，例如“知识草稿”在待办中仍以标签和筛选出现。
- [风险] 三栏审核在小屏下拥挤 → 桌面三栏，窄屏纵向排列或分段 Tabs。
- [风险] 行动总览可能过度强调问题数量造成焦虑 → 使用中性后台语气，显示“待处理”“可优化”“配置提醒”，避免营销式夸张文案。
- [风险] 配置清单需要跨模块跳转，可能中断当前工作 → 使用当前页面内 Modal/Drawer 优先，必要时跳转到 Bot/MCP 页面并保留返回路径。

## 迁移计划

1. 先实现信息架构调整和静态聚合逻辑，确保现有 API 可支撑页面。
2. 在不删除原能力的情况下，把旧 Tab 内容迁移到新的文档、待办、反馈闭环、配置、分析工作区。
3. 保留现有 URL `/wiki` 和 namespace 选择逻辑，不引入路由迁移。
4. 若上线后发现性能问题，再补充聚合 API；前端可回退到原有各 API 并行请求。
5. 回滚时恢复原 Tab 配置和现有组件布局，不影响后端数据。

## 开放问题

- 统一待办的优先级排序是否需要支持管理员自定义，还是先固定为：配置错误 > 新负反馈 > 高频无命中 > 待审核草稿 > 正反馈标注？
- 草稿审核三栏是否继续放在 Modal 中，还是在桌面端提供可选的全屏 Drawer/独立页面？
- 分析区是否需要趋势图，还是本轮只保留当前 Statistic/List 风格的轻量指标？
