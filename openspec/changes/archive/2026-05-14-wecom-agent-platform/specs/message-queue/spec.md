## 新增需求

### 需求:per-chatKey 串行消息队列
系统必须为每个 chatKey 维护独立的串行消息队列，保证同一会话的消息按顺序处理。

#### 场景:同一 chatKey 消息串行处理
- **当** 同一 chatKey 在前一条消息处理完成前收到新消息
- **那么** 新消息必须进入该 chatKey 的队列等待，不得并发处理

#### 场景:不同 chatKey 消息并行处理
- **当** 不同 chatKey 同时收到消息
- **那么** 各 chatKey 的队列独立运行，互不阻塞，并行处理

#### 场景:队列任务失败不中断队列
- **当** 队列中某个任务（消息处理）抛出异常
- **那么** 系统必须捕获异常并记录日志，继续处理队列中的下一个任务，不中断整个队列

### 需求:队列积压保护
系统必须在队列积压过多时给用户反馈，防止无限等待。

#### 场景:队列积压超限提示
- **当** 某个 chatKey 的队列中待处理消息数量超过 10 条
- **那么** 系统必须立即回复该消息"当前处理队列繁忙，请稍后再试"，不将该消息加入队列

### 需求:消息去重
系统必须防止企业微信 SDK 重试机制导致的重复消息处理。

#### 场景:重复消息跳过处理
- **当** 收到 msgid 与已处理消息相同的消息
- **那么** 系统必须跳过该消息，不加入队列，不回复

#### 场景:去重缓存大小限制
- **当** 已处理消息 ID 缓存超过 1000 条
- **那么** 系统必须删除最早加入的记录，保持缓存大小不超过 1000 条

### 需求:"思考中"消息占位
系统必须在开始处理消息时立即发送占位消息，处理完成后替换为真实回复。

#### 场景:发送占位消息
- **当** 消息任务开始执行（出队列开始处理）
- **那么** 系统必须立即发送"🤔 正在分析，请稍候..."消息，并保存返回的 messageId

#### 场景:替换占位消息
- **当** Agent 处理完成，生成真实回复
- **那么** 系统必须尝试 editMessage(messageId, 真实回复)；若 editMessage 不支持或失败，则 fallback 发送新消息
