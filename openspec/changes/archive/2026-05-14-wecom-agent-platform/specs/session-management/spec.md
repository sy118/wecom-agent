## 新增需求

### 需求:内存会话存储
系统必须为每个 chatKey 维护独立的内存会话，存储对话历史，支持多轮对话。

#### 场景:首次消息建立会话
- **当** 某个 chatKey 发来第一条消息且无现有会话
- **那么** 系统创建新 Session，记录 contextId、初始化空消息列表、设置 lastActiveAt 和 expiresAt（当前时间 + TTL）

#### 场景:后续消息复用会话
- **当** 某个 chatKey 发来消息且存在未过期的会话
- **那么** 系统复用现有 Session，将新消息追加到消息列表，更新 lastActiveAt 和 expiresAt

#### 场景:会话过期后重建
- **当** 某个 chatKey 发来消息但会话已过期（当前时间 > expiresAt）
- **那么** 系统删除旧会话，创建新会话，从空消息列表开始新的对话

### 需求:会话上下文窗口限制
系统必须限制每个会话保留的消息数量，防止 token 超限。

#### 场景:消息数量超限时截断
- **当** 会话消息列表长度超过 20 条
- **那么** 系统必须从列表头部删除最早的消息，保持列表长度不超过 20 条（HumanMessage 和 AIMessage 各计一条）

#### 场景:截断不影响当前处理
- **当** 截断发生时
- **那么** 截断操作必须在将新消息加入列表之前完成，确保 Agent 始终收到最新的 20 条消息

### 需求:会话 TTL 自动清理
系统必须定期清理过期会话，释放内存。

#### 场景:定时清理过期会话
- **当** 系统每分钟执行一次清理检查
- **那么** 系统必须删除所有 expiresAt < 当前时间的会话记录

#### 场景:TTL 可按上下文配置
- **当** 上下文配置了 session_ttl_min（默认 30 分钟）
- **那么** 该上下文下创建的所有会话必须使用对应的 TTL 值

### 需求:手动清除会话
管理员必须能够通过 API 强制清除指定 chatKey 的会话。

#### 场景:手动清除会话
- **当** 管理员通过 API DELETE /api/sessions/:chatKey
- **那么** 系统立即删除该 chatKey 的内存会话，下次消息将从空上下文开始
