# wiki-knowledge-review 规范

## 目的
定义 Wiki 知识草稿、审核合并、反馈分流和反馈转草稿的知识改进闭环，确保自动提炼或用户反馈产生的知识先经过管理员审核再进入正式 Wiki。
## 需求
### 需求: Wiki 知识草稿

系统必须支持将自动提炼的知识先保存为草稿，而不是默认直接写入正式 Wiki 页面。

#### 场景: 创建知识草稿

- **当** Bot、Skill、定时任务或无命中问题提炼出候选知识
- **那么** 系统必须允许将候选知识保存为草稿
- **并且** 草稿必须包含 namespace、建议页面路径、Markdown 内容、来源类型、来源引用和状态

#### 场景: 查看待审核草稿

- **当** 管理员进入 namespace 的知识草稿区域
- **那么** 页面必须展示待审核草稿列表
- **并且** 支持查看 Markdown 内容预览、来源信息、目标页面和当前状态

### 需求: 草稿审核

系统必须支持管理员批准或拒绝知识草稿。

#### 场景: 批准草稿

- **当** 管理员批准某条草稿
- **那么** 系统必须根据管理员选择的合并策略写入、追加或创建目标 Markdown 页面
- **并且** 执行 Git commit
- **并且** 将草稿状态更新为已合并

#### 场景: 拒绝草稿

- **当** 管理员拒绝某条草稿并填写原因
- **那么** 系统必须将草稿状态更新为已拒绝
- **并且** 保存拒绝原因
- **并且** 不得修改正式 Wiki 文件

#### 场景: 审核操作失败

- **当** 写入文件、Git commit 或状态更新失败
- **那么** 系统必须返回明确错误
- **并且** 不得将草稿错误标记为已合并

### 需求: wiki-compiler 默认进入草稿流程

系统必须将 wiki-compiler 的推荐使用方式调整为生成知识草稿。

#### 场景: wiki-compiler 提炼新知识

- **当** wiki-compiler 判断对话中存在可沉淀知识
- **那么** 推荐流程必须创建 Wiki 知识草稿
- **并且** 由管理员审核后再写入正式 Wiki

### 需求: 反馈事件来源草稿
系统必须支持从用户反馈事件创建 Wiki 知识草稿。

#### 场景: 草稿记录反馈来源
- **当** 系统从用户反馈创建知识草稿
- **那么** 草稿的来源类型必须为 `feedback-event`
- **并且** 来源引用必须包含反馈处理项和回复追踪记录的可追溯标识

#### 场景: 审核反馈来源草稿
- **当** 管理员打开来源类型为 `feedback-event` 的草稿详情
- **那么** 系统必须展示原问题、原回答、用户反馈内容、负反馈原因和检索证据
- **并且** 管理员必须能够编辑草稿内容后再合并

#### 场景: 合并反馈来源草稿
- **当** 管理员批准来源类型为 `feedback-event` 的草稿
- **那么** 系统必须按现有合并策略写入 Wiki
- **并且** 将关联反馈处理项标记为已解决

### 需求: 草稿编辑
系统必须允许管理员在合并前编辑 Wiki 知识草稿。

#### 场景: 编辑草稿内容
- **当** 管理员打开待审核草稿详情并修改 Markdown 内容
- **那么** 系统必须保存修改后的草稿内容
- **并且** 草稿状态必须保持为待审核

#### 场景: 编辑目标页面路径
- **当** 管理员修改草稿的目标页面路径
- **那么** 系统必须校验路径合法性
- **并且** 禁止保存包含上级目录跳转或绝对路径的目标路径

### 需求: 合并前差异预览
系统必须在草稿合并前展示目标页面的差异预览。

#### 场景: 预览追加合并差异
- **当** 管理员选择追加合并策略
- **那么** 系统必须展示目标页面当前内容与追加草稿后的差异

#### 场景: 预览覆盖合并差异
- **当** 管理员选择覆盖合并策略
- **那么** 系统必须展示目标页面当前内容与草稿内容之间的差异

#### 场景: 目标页面不存在
- **当** 草稿目标页面不存在
- **那么** 差异预览必须明确展示将创建新页面

### 需求: 合并策略
系统必须支持管理员选择草稿合并策略。

#### 场景: 追加合并
- **当** 管理员选择 `append` 策略并批准草稿
- **那么** 系统必须将草稿内容追加到目标 Markdown 页面
- **并且** 将草稿状态更新为已合并

#### 场景: 覆盖合并
- **当** 管理员选择 `replace` 策略并批准草稿
- **那么** 系统必须使用草稿内容覆盖目标 Markdown 页面
- **并且** 将草稿状态更新为已合并

#### 场景: 仅创建新页面
- **当** 管理员选择 `createOnly` 策略并批准草稿
- **那么** 系统必须仅在目标页面不存在时创建页面
- **并且** 如果目标页面已存在，系统必须拒绝合并并返回明确错误

### 需求: Wiki 反馈收件箱
系统必须在 Wiki 运营能力中提供用户反馈收件箱。

#### 场景: 查看新反馈
- **当** 管理员进入 Wiki 反馈收件箱
- **那么** 系统必须展示未处理反馈列表
- **并且** 每条反馈必须展示反馈类型、负反馈原因、用户补充内容、关联问题、机器人回答和创建时间

#### 场景: 查看反馈证据
- **当** 管理员打开反馈详情
- **那么** 系统必须展示关联回复的 Wiki 检索 query、命中文档、命中数量、耗时和错误信息
- **并且** 如果没有关联回复，系统必须明确标识该反馈无法反查原始回答

### 需求: 反馈分流
系统必须允许管理员对反馈进行分流处理。

#### 场景: 标记为知识缺失
- **当** 管理员将反馈标记为知识缺失或内容不完整
- **那么** 系统必须允许管理员从该反馈创建 Wiki 草稿

#### 场景: 标记为检索问题
- **当** 管理员将反馈标记为检索问题
- **那么** 系统必须保存处理状态和备注
- **并且** 禁止自动创建 Wiki 草稿

#### 场景: 标记为模型或工具问题
- **当** 管理员将反馈标记为模型问题、工具问题或数据分析错误
- **那么** 系统必须保存处理状态和备注
- **并且** 该反馈必须继续计入质量指标

#### 场景: 忽略反馈
- **当** 管理员确认某条反馈无需处理
- **那么** 系统必须将反馈标记为已忽略
- **并且** 保存忽略原因

### 需求: 反馈转 Wiki 草稿
系统必须支持从用户反馈创建待审核 Wiki 草稿。

#### 场景: 从负反馈创建草稿
- **当** 管理员选择将负反馈转为 Wiki 草稿
- **那么** 系统必须预填目标 namespace、建议页面路径、原问题、原回答、反馈内容、负反馈原因和检索证据
- **并且** 草稿来源类型必须为 `feedback-event`

#### 场景: 草稿创建后关联反馈
- **当** 反馈成功创建 Wiki 草稿
- **那么** 系统必须将反馈状态更新为已生成草稿
- **并且** 保存草稿 ID 以便从反馈详情跳转到草稿审核

### 需求: 反馈运营指标
系统必须提供反馈质量指标，帮助管理员判断知识库和机器人质量趋势。

#### 场景: 查看反馈统计
- **当** 管理员查看 Wiki 运营页
- **那么** 系统必须展示选定时间窗口内的正反馈数、负反馈数、负反馈率、待处理反馈数和已转草稿数

#### 场景: 按原因聚合负反馈
- **当** 管理员查看负反馈原因分布
- **那么** 系统必须按企业微信负反馈原因聚合数量
- **并且** 区分知识缺失、检索问题、模型/工具问题和已忽略反馈

### 需求: 反馈证据驱动处理
系统必须在反馈详情中按照证据链组织信息，帮助管理员判断反馈根因。

#### 场景: 查看反馈证据链
- **当** 管理员打开用户反馈详情
- **那么** 页面必须展示用户反馈类型、负反馈原因、用户补充内容、原问题、机器人回答、关联会话和检索证据
- **并且** 页面必须突出可执行处理动作，例如标记检索问题、标记模型或工具问题、转 Wiki 草稿、创建标注答案或忽略

#### 场景: 反馈无法关联回答
- **当** 反馈没有关联回复追踪记录
- **那么** 页面必须明确展示未关联状态
- **并且** 禁止把该反馈伪装成可自动反查证据的反馈

### 需求: 三栏草稿审核
系统必须在草稿详情中提供来源证据、草稿内容和合并差异的并列审核体验。

#### 场景: 审核来源型草稿
- **当** 管理员打开待审核草稿详情
- **那么** 页面必须展示草稿来源证据、可编辑草稿内容和合并前差异预览
- **并且** 管理员必须能够在同一审核界面保存草稿、切换合并策略、批准合并或拒绝草稿

#### 场景: 小屏审核布局
- **当** 页面宽度不足以展示三栏审核
- **那么** 系统必须将来源证据、草稿内容和合并差异改为纵向区域或分段展示
- **并且** 禁止让按钮、文本或预览内容发生不可读重叠

### 需求: 反馈到草稿的状态联动
系统必须让反馈处理项、草稿和合并结果之间保持可追踪的状态联动。

#### 场景: 从反馈创建草稿后
- **当** 管理员从反馈详情创建 Wiki 草稿
- **那么** 页面必须跳转或打开对应草稿审核界面
- **并且** 反馈项必须展示已转草稿状态和草稿引用

#### 场景: 反馈来源草稿合并后
- **当** 管理员批准合并来源为反馈的草稿
- **那么** 页面必须将关联反馈展示为已解决
- **并且** 待办和总览中的反馈待处理数量必须刷新
