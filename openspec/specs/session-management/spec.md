# 会话管理 (Session Management)

## 目的

为每个 chatKey 维护独立的持久化会话，支持多轮对话、上下文窗口限制、TTL 自动清理及手动清除能力。会话数据持久化到 SQLite，进程重启后可恢复。
## 需求
### 需求:持久化会话存储
系统必须为每个 chatKey 维护独立的**持久化**会话，存储对话历史，支持多轮对话。会话数据必须持久化到 SQLite，进程重启后能够恢复。

#### 场景:首次消息建立会话
- **当** 某个 chatKey 发来第一条消息且无现有会话（数据库中不存在或已过期）
- **那么** 系统创建新 Session，记录 contextId、初始化空消息列表、设置 lastActiveAt 和 expiresAt（当前时间 + TTL），并将会话元数据写入 SQLite

#### 场景:后续消息复用会话
- **当** 某个 chatKey 发来消息且数据库中存在未过期的会话
- **那么** 系统从 SQLite 加载会话，复用现有 Session，将新消息追加到消息列表，更新 lastActiveAt 和 expiresAt

#### 场景:进程重启后恢复会话
- **当** 服务进程重启后，用户发来消息
- **那么** 系统必须从 SQLite 恢复该 chatKey 的会话历史（若未过期），用户无需重新开始对话

#### 场景:会话过期后重建
- **当** 某个 chatKey 发来消息但会话已过期（当前时间 > expiresAt）
- **那么** 系统删除旧会话（包括 SQLite 中的记录），创建新会话，从空消息列表开始新的对话

### 需求:会话上下文窗口限制
系统必须限制每个会话保留的消息数量，防止 token 超限。

#### 场景:消息数量超限时截断
- **当** 会话消息列表长度超过 20 条
- **那么** 系统必须从列表头部删除最早的消息，保持列表长度不超过 20 条（HumanMessage 和 AIMessage 各计一条）

#### 场景:截断不影响当前处理
- **当** 截断发生时
- **那么** 截断操作必须在将新消息加入列表之前完成，确保 Agent 始终收到最新的 20 条消息

### 需求:会话 TTL 自动清理
系统必须定期清理过期会话，释放内存。

#### 场景:定时清理过期会话
- **当** 系统每分钟执行一次清理检查
- **那么** 系统必须删除所有 expiresAt < 当前时间的会话记录

#### 场景:TTL 可按上下文配置
- **当** 上下文配置了 session_ttl_min（默认 30 分钟）
- **那么** 该上下文下创建的所有会话必须使用对应的 TTL 值

### 需求:手动清除会话
管理员必须能够通过 API 强制清除指定 chatKey 的会话。

#### 场景:手动清除会话
- **当** 管理员通过 API DELETE /api/sessions/:chatKey
- **那么** 系统立即删除该 chatKey 的 SQLite 会话记录，下次消息将从空上下文开始

### 需求:消息内容预处理（去除 @前缀）
系统必须在将消息内容传递给 LLM 之前，自动去除群聊消息中的 `@机器人名字` 前缀。

#### 场景:群聊消息去除 @前缀
- **当** 收到群聊（`chattype=group`）的文本消息，内容以 `@` 开头
- **那么** 系统必须用正则 `/^@\S+\s*/` 去除前缀，LLM 只接收用户的实际问题

#### 场景:单聊消息不受影响
- **当** 收到单聊（`chattype=single`）的文本消息
- **那么** 系统禁止修改消息内容，直接传递给 LLM

#### 场景:不含 @前缀的群聊消息不受影响
- **当** 收到群聊消息但内容不以 `@` 开头
- **那么** 系统禁止修改消息内容

### 需求: 会话消息关联回复追踪
系统必须支持将会话消息与机器人回复追踪记录关联。

#### 场景: 保存用户消息关联
- **当** Bot 开始处理一条用户消息并创建回复追踪记录
- **那么** 系统必须在保存该用户消息时关联回复追踪记录 ID

#### 场景: 保存机器人消息关联
- **当** Bot 完成回复并保存机器人消息
- **那么** 系统必须在保存该机器人消息时关联同一回复追踪记录 ID

#### 场景: 从反馈反查会话片段
- **当** 管理员查看用户反馈关联的回复追踪记录
- **那么** 系统必须能够查询对应会话消息
- **并且** 展示足够定位问题的原始问答片段

### 需求:平台默认会话 TTL 配置
系统必须提供平台级默认会话 TTL 配置，用于决定新建上下文在未显式指定会话 TTL 时的默认 `sessionTtlMin`；上下文级 TTL 仍是 session 实际生效配置。

#### 场景:新建上下文使用平台默认 TTL
- **当** 管理员创建上下文且未显式指定 `sessionTtlMin`
- **那么** 系统必须使用平台默认会话 TTL 作为该上下文的 `sessionTtlMin`

#### 场景:显式 TTL 优先于平台默认值
- **当** 管理员创建上下文并显式指定 `sessionTtlMin`
- **那么** 系统必须使用请求中的 `sessionTtlMin`，禁止用平台默认会话 TTL 覆盖该值

#### 场景:修改平台默认 TTL 不覆盖已有上下文
- **当** 管理员修改平台默认会话 TTL
- **那么** 系统禁止修改已有上下文的 `sessionTtlMin`

#### 场景:平台默认 TTL 校验
- **当** 管理员设置平台默认会话 TTL
- **那么** 系统必须校验该值为允许范围内的正整数分钟数

#### 场景:存量 session 不立即重算过期时间
- **当** 平台默认会话 TTL 发生变化
- **那么** 系统禁止立即重算已存在 session 的 `expiresAt`

#### 场景:会话仍使用上下文 TTL 滑动续期
- **当** 某个 chatKey 发来消息且对应上下文已有 `sessionTtlMin`
- **那么** 系统必须继续使用该上下文的 `sessionTtlMin` 计算或刷新 session 的 `expiresAt`

### 需求:上下文切换后会话隔离
系统必须在上下文切换成功后隔离新旧上下文的会话历史，禁止新上下文复用旧上下文的消息历史或 Dify conversationId。

#### 场景:切换上下文后清理旧会话
- **当** 用户成功执行 `/ctx use ctx-a`
- **那么** 系统必须清理该 botId 和 chatKey 下会导致污染的活跃 Session
- **并且** 下一条普通消息必须从新上下文的空会话开始

#### 场景:Dify conversationId 不跨上下文复用
- **当** 旧会话包含 `difyConversationId`
- **并且** 用户切换到新上下文
- **那么** 系统禁止在新上下文请求中携带旧 `difyConversationId`

#### 场景:切换失败不清理会话
- **当** 用户尝试切换到无权限上下文失败
- **那么** 系统禁止清理当前活跃 Session

### 需求:上下文兼容的会话复用
系统必须只在当前消息解析出的有效上下文与活跃 Session 的上下文兼容时复用会话；如果上下文已发生运行时切换，系统必须创建或使用该上下文隔离后的新会话。

#### 场景:同一上下文复用会话
- **当** 某个 chatKey 发来消息且数据库中存在未过期的会话
- **并且** 当前生效 contextId 与该会话 contextId 一致
- **那么** 系统必须从 SQLite 加载会话并复用现有 Session

#### 场景:上下文变更不复用旧会话
- **当** 某个 chatKey 发来消息且数据库中存在未过期的旧会话
- **并且** 当前生效 contextId 与旧会话 contextId 不一致
- **那么** 系统必须禁止把旧会话消息传给模型
- **并且** 必须创建或加载当前 contextId 对应的隔离会话
